Set up the repository, verify your change, and prepare it for independent review.

## Prerequisites

- A local checkout of this repository.
- The Node version in `.node-version` and the pnpm version in `package.json`.
- The root `AGENTS.md` and the instructions for any package you change.

## Local setup

### 1. Install dependencies and build

From the repository root:

```bash
pnpm install --frozen-lockfile
pnpm build
```

Expected result: pnpm installs the locked dependencies and Nx builds packages
in dependency order. A successful build exits with status 0.

### 2. Make your change

Follow the workflow and conventions below.

## Before submitting a PR

### 3. Run the checks

From the repository root:

```bash
pnpm build
pnpm test
pnpm check
```

Expected result: Nx reports successful build and test targets; lint and
format checks exit with status 0. Build before lint so typed linting can
resolve package declarations.

`pnpm check` runs `pnpm lint` and `pnpm format:check`. For a documentation
change, also run the link check from the repository root:

```bash
pnpm docs:check
```

Expected result: no broken internal links.

## Monorepo conventions

- **Package manager**: pnpm 10+ with workspaces
- **TypeScript**: strict mode, ES modules
- **Runtime model**: Effect services and typed error channels
- **Formatting**: oxfmt
- **Testing**: vitest
- **Task graph**: Nx derives package order from declared dependencies

## Workflow

Understand the task, decide if needed, implement and test, obtain independent
review, then ship. A routine fix stays in its issue/PR. A coordinated feature
gets one plan; a durable design choice gets one complete ADR with source
evidence, independent review, and explicit owner approval. The original request
or issue authorizes bounded implementation without another approval ritual.

Public specifications in `docs/vision.md` and `docs/spec/`, together with the
checks in this repository, are the authority for every contribution. A new
boundary choice updates its public specification before implementation.

## Architecture checks

`pnpm lint` runs `arch:check` for every package through
`safer-architecture-lsp check .`. Run `pnpm arch:check` from the repository root
to analyze every package on its own. Successful analysis exits with status 0;
findings exit 1, and a project that cannot be analyzed exits 2.

Edit each package's `safer-architecture.config.json` by hand to change its
budgets, domains, and entrypoints. Exceptions are `safer-arch-ignore` directives in the source, most at the top of the file
they cover. List them from the repository root:

```bash
rg -n "safer-arch-ignore" packages/*/src
```

Expected output: matching source paths, line numbers, and directives.

Raising a budget or adding a directive is an architecture review point: say so
in the PR description.

## Documentation

The docs site at `docs/` is built with
[Mintlify](https://mintlify.com). TypeDoc builds the API reference directly
from source JSDoc with `pnpm docs:api`; open `dist/api/index.html` afterward.
The standalone HTML reference is separate from the Mintlify site.

| Command | What it does |
|---------|--------------|
| `pnpm run docs:dev` | Preview locally without opening a browser |
| `pnpm run docs:open` | Preview locally and open a browser |
| `pnpm docs:api` | Build TypeDoc HTML in `dist/api` |
| `pnpm docs:check` | Check for broken internal links |

- **Guides and development pages**: edit the MDX files directly in `docs/`.
- **API reference**: edit JSDoc on the owning symbol, then run `pnpm docs:api`.
- **Reusable content**: use [Mintlify snippets](https://www.mintlify.com/docs/create/reusable-snippets)
  under `docs/snippets/` and [global variables](https://www.mintlify.com/docs/organize/settings-reference#variables)
  in `docs/docs.json`. Keep each documentation value in one place.
- **Wire examples**: use `WIRE_VERSION` from Client's identity module; the
  [wire version contract](/spec/identity#wire-versions) names its source.

## Code style

- Decode network, disk, environment, and dynamic-import inputs with Effect
  `Schema`.
- Declare branded domain values in their owning package.
- Keep typed errors in the Effect error channel.
- Prefer integration tests at real process and storage boundaries.

## Maintainer releases and records

### Branches and releases

- `main` is the only long-lived branch; every change lands there by pull
  request.
- A user-visible change adds a fragment under `changelog.d/` (see
  `towncrier.toml`); merging it releases after CI passes on `main`. Resets,
  resumes and abandoned releases are maintainer dispatches of
  `.github/workflows/publish.yml`, described in
  [Publication and versions](/spec/layer-interfaces#publication-and-versions)
  and the workflow's header.
- The OpenClaw and NanoClaw agent images are built and published outside
  this repository, not by a release here.
- Public design contracts live in `docs/vision.md` and `docs/spec/`; see
  `AGENTS.md` for package-specific instructions.

## Next steps

- Obtain independent review and submit your pull request using the workflow
  in `AGENTS.md`.
- Read the [architecture](/architecture) and applicable
  [specifications](/spec/layer-interfaces) before changing a package boundary.
- Follow the [upgrade guide](/guides/upgrades) when deploying a reset release.
