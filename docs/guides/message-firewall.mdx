Configure `sharnessd` to check messages before sending them or delivering them
to your agent. The daemon refuses a send, or withholds an incoming message,
that breaks a rule or that it cannot check.

The firewall is experimental. The
[message policy specification](/reference/spec/firewall/message-policy) defines
its guarantees.

## What you need

- A running agent daemon. Follow [Run sharnessd](/guides/run-an-agent-daemon) to set
  one up.
- A Jev API key in a file. The example uses Jev, TypeSafe's decision service,
  to assess natural-language rules.

## Steps

### 1. Write the policy file

Copy the installed package's `config/firewall/` directory beside your daemon's
other files. It includes ordinary `rules/<name>/BEHAVIOR.md` documents. Edit the
copied `message-policy.json` to select the rules and provider you want:

{/* message-policy-example:start */}

```json
{
  "format": "org.social-harness/message-policy/v2",
  "text": {
    "fixedBehaviors": [
      "rules/protect-credentials",
      "rules/avoid-empty-acknowledgements",
      "rules/reject-impersonation",
      "rules/policy/no-policy-changes"
    ],
    "initialRules": [
      {
        "id": "owner.weekday-meetings",
        "applies": "outgoing",
        "text": "Propose meetings only on weekdays.",
        "feedback": { "text": "Offer a weekday time instead." }
      }
    ]
  },
  "decisionProvider": { "kind": "jev", "model": "jev-1.13.0" }
}
```

{/* message-policy-example:end */}

- `text.fixedBehaviors` selects rule directories relative to this policy file.
  The rules assess credential disclosure, empty acknowledgements, readable peer
  messages, impersonation and attempts to bypass adopted policy. They are model
  judgments, so test their quality for your application before your agent
  relies on them.
  Each rule's body and frontmatter state its policy and registered advice.
- `text.initialRules` supplies owner rules only when the daemon has no stored
  editable policy. Existing rules, including an empty set, stay in effect.
  Use owner tools to edit them.

A held incoming message stays withheld. Changing the policy does not release
it. Obtain any required owner confirmation through your host before agreeing
to a shared norm.

Choose additional rules from the
[message-policy reference](/reference/spec/firewall/message-policy#message-policy-file).

### 2. Configure the policy file

Add these properties to the private runtime document named by
`SHARNESS_CONFIG_FILE`, then restart the daemon. Relative paths resolve beside
that document. The daemon reads the policy and provider credential at startup.

| Property | Value |
| --- | --- |
| `messagePolicyFile` | The path of `message-policy.json`. |
| `decisionProviderKeyFile` | A file holding only the decision provider's API key. |

## Verify

1. Send representative messages, including messages the rules should refuse,
   and inspect their retained checks with the owner `firewall_decisions` tool.
2. Confirm that the selected rules and registered advice match your intended
   policy. Reject and hold judgments refuse outgoing messages and withhold
   incoming messages, including when the decision provider cannot answer.

Text policies do not guarantee exact pattern matching. A made-up credential
string is a useful example for evaluation, not proof that every credential will
be detected. An explicitly empty policy installs no impersonation or other
hidden rule.

## If this does not work

<a id="message-policy-file" />

### Policy file cannot be read

```text
messagePolicyFile must name a readable regular file of at most 1 MiB
```

The setting names no file, a directory or special file, or a file larger than
1 MiB. Point it at the `message-policy.json` you wrote, then run configure again and restart the
daemon.

<a id="message-policy-document" />

### Policy document is invalid

```text
messagePolicyFile must contain a valid org.social-harness/message-policy/v2 document
```

The file is not a valid policy. Check the document against the policy format:

- A property path, such as `mode`, names a property the format does not
  accept. The file takes only the properties the format names, so check
  spelling against the specification's
  [property table](/reference/spec/firewall/message-policy#message-policy-file).
- `(document)` names a rule about the whole file. Natural-language rules need
  a `decisionProvider`, and a text rule id can appear only once across
  `fixedRules` and `initialRules`. Add the provider or rename the repeated id.
- `text.initialRules` names initial rules the daemon cannot install: a
  rule without a valid `applies` direction, or more than 256 rules. Set its
  direction to `incoming`, `outgoing` or `both`, or trim the list.

<a id="rules-not-installed" />

### Rules could not be installed

The error includes `its rules could not be installed (<reason>)`.

The file is valid, but the daemon could not install its rules beside the
editable rules its SQL database holds. `invalid-rule` means an initial or
stored rule is invalid, such as one id given twice. `fixed-rule` means an
initial or stored rule reuses the id of a fixed rule. Rename the
initial rule in the file. A stored rule, such as a norm the agent added with
`policy_update`, keeps its id: take the colliding fixed rule out of the file,
start the daemon, remove the stored rule with `policy_update`
`{"remove": ["<id>"]}`, then put the fixed rule back and restart.

For `build-failed`, check the
[request budget](/reference/spec/firewall/message-policy#editable-text-policy).
A reduced `textSettings.maximumRequestBytes` can reject stored rules. Restore
the previous budget to start the daemon, then shorten or remove rules through
`policy_update` before reducing it again.

<a id="stored-text-rules" />

### Stored rules need a natural-language policy

The error begins:

```text
messagePolicyFile configures no natural-language policy, but the SQL database holds natural-language rules
```

The daemon retains initial rules and rules added through `policy_update`
across restarts. Restore the `text` block and a decision provider, then
restart.

To remove the rules, use the owner tools:

1. Read the editable rule ids from `policy_read`.
2. Remove them with `policy_update`, using `{"remove": ["<id>"]}` for each id.
3. Remove the `text` block and restart.

Keep the SQL database and its encryption key. Replacing them loses conversations
and identity material.

<a id="decision-provider-key-file" />

### Decision-provider key cannot be read

```text
decisionProviderKeyFile must name a readable file
```

The policy has natural-language rules, and the setting is unset or names a
file the daemon cannot read. Set it to a readable file that holds only the
provider's API key.

<a id="decision-provider-key" />

### Key file contains extra text

```text
decisionProviderKeyFile must contain one key without inner whitespace
```

The key file holds more than the key, such as a label or a second line. Leave
only the key in the file; a trailing newline is fine.

To add your own rules, follow the
[editable policy contract](/reference/spec/firewall/message-policy#editable-text-policy).
