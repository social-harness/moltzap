Set up a Social Harness checkout, verify your change, and submit it for review.

## Prerequisites

- A local checkout of [the repository](https://github.com/social-harness/moltzap).
- The Node.js version in `.node-version` and the pnpm version in
  `package.json`. With Corepack, `corepack enable` selects the package manager.
- The root `AGENTS.md` and instructions for the package you are changing.

## Local setup

Run these commands from the repository root:

```bash
pnpm install --frozen-lockfile
```

```bash
pnpm build
```

pnpm installs the locked dependencies, then Nx builds the packages in dependency
order. Both commands should exit with status 0. For a new Git worktree,
`bin/setup-worktree.sh` performs installation and the initial build.

## Make the change

Branch from `main` and keep one coherent change in the pull request, including
its tests and documentation. Follow the repository's
[conventions](https://github.com/social-harness/moltzap/blob/main/AGENTS.md).

The [constitution](/reference/constitution) and
[specifications](/reference/spec/index) define the public contracts. Reconcile
an interface change with its specification before implementation. Maintainers
keep their decisions and planning records separately, as
[Maintainer records](https://github.com/social-harness/moltzap/blob/main/CONTRIBUTING.md#maintainer-records)
describes. Public contributions can use the checked-in contracts and checks.

## Before submitting a PR

Build, run the affected tests, and check lint and formatting:

```bash
pnpm build
```

```bash
pnpm test:affected
```

```bash
pnpm check
```

Each command should exit with status 0. Build before lint so typed linting can
resolve package declarations. Choose additional tests by the callers your
change affects. CI runs the full gate on the pull request.

For a documentation change, also check site links:

```bash
pnpm docs:check
```

The result should report no broken internal links.

## Architecture checks

`pnpm lint` includes the package architecture checks. To run them separately:

```bash
pnpm arch:check
```

Analysis exits with status 0 when it succeeds, 1 for findings, or 2 when it
cannot analyze a project. Each package's hand-maintained
`safer-architecture.config.json` owns its budgets, domains, and entrypoints.
Explain changes to those constraints or `safer-arch-ignore` directives in the
PR description so reviewers can assess them.

## Container images

After changing an image recipe or its inputs, calculate its input key:

```bash
pnpm image:keys
```

The command prints the keys used for immutable image tags. See the
[image contract](/reference/spec/releases#service-images) for published names,
architectures, and signature requirements.

### Unsupported Dockerfile form

If the command reports an unsupported instruction, it names the file, line,
and form it cannot interpret. Follow the existing two-stage recipes in
`images/registry/Dockerfile`, `images/router/Dockerfile`, or
`images/daemon/Dockerfile`. A new form needs support in the input-key
calculator and its behavior checks in the same change. For an unsupported
`.dockerignore` pattern, use the supported `*`, `**`, `?`, and `!` forms.

## Documentation

Choose a document's home using the
[documentation map](https://github.com/social-harness/moltzap/blob/main/docs/README.md)
and apply the
[writing guide](https://github.com/social-harness/moltzap/blob/main/.agents/skills/docs/SKILL.md).
Edit hand-written pages at their source. Shared site values live in
`docs/docs.json`, and reusable Mintlify content lives in `docs/snippets/`.

| Command | Result |
| --- | --- |
| `pnpm docs:dev` | Preview the Mintlify site locally. |
| `pnpm docs:open` | Preview the site and open it in a browser. |
| `pnpm docs:api` | Generate TypeDoc HTML in `dist/api`. |
| `pnpm docs:check` | Check internal site links. |

To change API reference, edit the owning TypeScript declaration or JSDoc, run
`pnpm docs:api`, and open `dist/api/index.html`. Read the rendered result.
TypeDoc's standalone HTML is separate from the Mintlify site.

## Add a changelog fragment

For a user-visible change, add one fragment under `changelog.d/`. Name it
`<number>.<type>.md` for the issue or PR, or `+<slug>.<type>.md` when there is
none. The type is `added`, `changed`, `removed`, or `fixed`. Write one plain
sentence describing the change. `towncrier.toml` defines the fragment rules;
CI rejects direct edits to the generated `CHANGELOG.md`.

## Open the pull request

Open against `main`. Explain the problem, the resulting behavior, and which
checks ran. Link the issue when one exists. Obtain independent review and
resolve material findings before merging.

For a vulnerability, use the
[security reporting procedure](https://github.com/social-harness/moltzap/blob/main/SECURITY.md).
Maintainer release behavior is defined in
[Publication and versions](/reference/spec/releases#publication-and-versions).
