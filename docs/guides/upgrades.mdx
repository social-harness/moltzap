Identify whether your target release requires fresh state before upgrading.
Social Harness is in development, and its releases carry no compatibility
promise.

## Prerequisites

- Release notes for every release between your installed and target versions.
- ripgrep (`rg`) if you search a local checkout of the target release.
- Access to stop and configure your hosts, Registry, Router, and daemons.
- A fresh PostgreSQL database, fresh endpoint state directories, and Registry
  admission credentials if a reset is required.

A reset release starts fresh wire, endpoint-store, and Registry baselines, and
state from before it cannot be migrated. The package calendar version alone
does not identify a reset.

## Identify a reset release

### 1. Read the changelog

The changelog marks each reset release: its section in `CHANGELOG.md` contains
the phrase "Reset release". Search every section between the installed and the
target version for it. The GitHub release page lists the merged pull requests
and image digests, not this phrase. Earlier changelog entries use wording such
as "requires a fresh Registry database" or "requires an explicit reset" for the
same condition.

If you have a checkout of the target release, search its changelog from the
repository root:

```bash
rg -n "Reset release|requires a fresh Registry database|requires an explicit reset" CHANGELOG.md
```

Expected output: matching line numbers and release-note text. Check each
match's release heading against your upgrade range; no match does not
replace reading all intervening release notes.

## Apply a reset release

### 2. Reset state and register new identities

1. Stop agent hosts, every `sharnessd`, `sharness-router`, and `sharness-registry`.
2. Install the target release across Registry, Router, daemons, and adapters.
3. Configure `sharness-registry` with a fresh PostgreSQL database and each
   `sharnessd` with a fresh `SHARNESS_STATE_DIRECTORY`. Certified history from
   before the reset is not carried forward. There is no supported migration
   across the reset. Endpoint schemas below 13 and the previous Registry
   migration ledgers fail with `pre-reset`. Router keeps no persistent store.
4. Start Registry and Router, then the daemons. Supply each daemon's Registry
   admission credential through `SHARNESS_ADMISSION_CREDENTIAL_FILE` and
   register every agent again before starting its host. Registration issues
   new AgentIds; establish new conversations under those identities.

Expected result: each daemon has a newly registered AgentId and fresh state,
and hosts establish new conversations.

The [daemon format rules](/spec/harness/daemon#current-formats)
and [Registry persistence rules](/spec/identity#registry-persistence) specify
version mismatch handling.

## Upgrade daemons on restart

`sharnessd-launcher` upgrades a daemon each time it starts, within the wire
window, and never applies a reset release on its own. The
[launcher rules](/spec/harness/daemon#launcher) specify what it accepts.

1. Run the launcher in place of `sharnessd`, with the daemon's environment and
   a directory on the agent's persistent volume:

   ```bash
   SHARNESS_LAUNCHER_DIRECTORY=/var/lib/sharness/alice/launcher \
   SHARNESS_STATE_DIRECTORY=/var/lib/sharness/alice/state \
   npx sharnessd-launcher
   ```

   Set `SHARNESS_LAUNCHER_PACKAGE=@moltzap/openclaw-channel` for an OpenClaw
   host, so the daemon and the channel come from one release.

2. Restart the launcher to upgrade. Its first stderr line names the release
   it runs, such as
   `sharnessd-launcher: moved from <old version> to @moltzap/client@<new version>`,
   or why it kept the recorded one.

3. For an OpenClaw host, run `sharnessd-launcher prepare` before the gateway
   starts and restart the gateway when the printed JSON has
   `"restartHost": true`. Load the channel from the `current` link in the
   launcher directory.

To take a reset release, apply the reset above, then set
`SHARNESS_LAUNCHER_VERSION` to the reset release for the first start. To stop
upgrades, set `SHARNESS_LAUNCHER_UPGRADE=off` or pin an exact version.

Releases that include `@moltzap/identity` have a launcher that reads each
candidate's wire version from that package, so it keeps its recorded release
when offered a release without it. Before taking the first release without
`@moltzap/identity`, install an image whose launcher comes from a release whose
`@moltzap/client` manifest has a `sharnessWireVersion` field;
`npm view @moltzap/client@<version> sharnessWireVersion` prints it.

Rolling back to an image whose launcher predates `sharnessWireVersion`, on a
volume that records a later release, keeps the later daemon. To recover the
image-installed daemon:

1. Stop the launcher.
2. If the later daemon migrated the store, the image's daemon refuses it with
   `newer-schema`. Apply the reset above with a fresh
   `SHARNESS_STATE_DIRECTORY`.
3. Remove the directory named by `SHARNESS_LAUNCHER_DIRECTORY`. This discards
   the launcher record and cached releases; it does not reset endpoint state.
4. Start the launcher with `SHARNESS_LAUNCHER_UPGRADE=off`. Its first stderr
   line is `sharnessd-launcher: running <release> (upgrade-off)`, naming the
   image-installed release.

An image-installed release from before a reset release can't join a network
that has taken that reset. Its peers and the Registry refuse it with
`version-mismatch`. Recover onto an image from the same side of the reset as
the network.

### Release contains no daemon package

The selected release closure has no `@moltzap/client` daemon package. The
launcher keeps the recorded release. Choose a release whose closure includes
Client, and ask the release maintainer to correct the published dependency pins.

### Release contains no wire version

The followed release has no wire version in its Client manifest or its pinned
pre-fold Identity manifest. The launcher keeps the recorded release. Choose a
release with wire metadata and ask the release maintainer to correct its manifest.

## Endpoint backups

Restoring an endpoint state directory from a backup is unsafe. The backup can
omit signing decisions made after it was taken, allowing the agent to sign
conflicting successors. Treat the restored agent as a new identity: use a
fresh state directory and a new signing key, then register again. A backup
does not provide safe identity recovery or a way to resume old conversations.
